# Evaluation protocol (version 1)

Frozen before the held-out run. Any change after the freeze creates version 2,
and the report must say so.

## Question

Under identical workloads and identical injected faults, does evidence-gated,
failure-aware execution (`gated`) improve reliable completion, honest status
reporting and duplicate-effect avoidance over `sequential` and `naive-parallel`
execution, and what does it cost in simulated wall-clock time and tokens? We do
**not** presume it wins. Scenarios where it is worse are reported.

## Policies compared

| Policy | Concurrency | Deadlines | Retries | Verification | Duplicate delivery | Cancel |
|---|---|---|---|---|---|---|
| `sequential` | 1, precomputed topological order | none | up to 3 attempts on failure, crash, or invalid envelope | none: trusts the claim | immune (never consumes a second delivery) | stops starting tasks; in-flight finishes |
| `naive-parallel` | 4, dependency counters | none | same | none | none (counter decremented on every delivery) | stops starting tasks; in-flight finishes |
| `naive-parallel-timeout` | 4, dependency counters | same 3x nominal, worker aborted on expiry, late answer from the timed-out attempt dropped | same | none | none | stops starting tasks; in-flight finishes |
| `gated` | 4, state-derived readiness | 3x nominal | up to 3, retryable-classified | host-side gate | per-attempt dedup | aborts in-flight, starts nothing |
| `gated-sequential` (ablation) | 1 | 3x nominal | same | gate | dedup | aborts |

Baselines check envelope structure (artifact present, result well-formed) because
accepting a missing artifact would be a strawman. They do not check content.

`naive-parallel-timeout` is the **closest baseline**: it has the same deadlines and retry budget as `gated`, so
comparing against it isolates what the gate, per-attempt deduplication, effect-class recovery and cancellation
add *beyond* timeouts. Comparing against plain `naive-parallel` mostly measures the value of having any deadline.

## Workloads (dataset `workloads-v1`)

Five DAG shapes generated by `src/bench/workloads.js` from a fixed generator seed
and also stored as `bench/data/workloads-v1.json` (CI checks the stored file equals
regeneration): `chain-8`, `fanout-fanin-12`, `diamond-lattice-16`, `pipeline-24`, `random-dag-32`.

Per task: nominal latency 100 ms x U(0.8, 1.2); effect class drawn from a fixed hash of (generator seed, workload,
task) with target proportions `pure` 40%, `workspace-reversible` 20%, `external-idempotent` 20%,
`external-nonrepeatable` 20% (realized counts per workload are in `bench/data/workloads-v1.json`; `chain-8` happens to
contain no non-repeatable task); one `artifact_sha256` requirement over its single
output artifact, plus an `artifact_json` shape requirement on 50% of tasks. Output content is a pure
function of (task id, dependency output digests), so corruption propagates downstream.

## Fault profiles

The fate of attempt `k` of task `t` under seed `s` is `f(s, t, k)`, independent of policy (paired design).

| Profile | Injected per attempt |
|---|---|
| `none` | nothing |
| `crash` | before-effect crash 10%; after-effect crash (effect applied, result lost) 10%; non-repeatable tasks offer `reconcile` |
| `crash-noreconcile` | same, but no `reconcile` available |
| `delay` | latency x6 w.p. 15%; hang (never completes) w.p. 5% |
| `invalid_output` | malformed envelope / missing artifact w.p. 15% |
| `false_claim` | claims success with well-formed but wrong content w.p. 15% |
| `duplicate_delivery` | success envelope delivered twice w.p. 20% |
| `dependency_failure` | one designated task fails on every attempt |
| `cancel` | cancel requested at 50% of the workload's nominal critical path |
| `mixed` | crash 5%+5%, delay 8%, hang 2%, invalid 6%, false claim 6%, duplicate 10% |

## Fixed simulation parameters

Retry budget 3 attempts. Gated deadline 3x nominal. Gated retry backoff 20 simulated ms x attempt number.
Gate cost 5 simulated ms per requirement and 0 tokens. Token proxy: 10 tokens per simulated ms of worker time.
Hung attempts: a baseline waits until the run-level cap (30x the nominal critical path), after which remaining
tasks are recorded `unknown` and the run is flagged `incomplete`. Gated has no run-level cap beyond per-task deadlines.
Concurrency cap 4 for `naive-parallel` and `gated`.

## Seeds and splits

- Development seeds `0..99`: debugging only. No parameter above was chosen by looking at benchmark results.
- **Final seeds `10000..10499` (500 trials per cell).** Run once after the protocol commit. If a defect is found
  afterwards, fixes are committed and the whole final run is repeated; both runs are disclosed.

Cells: 5 workloads x 10 profiles x 5 policies x 500 seeds = 125,000 runs.

## Metrics

Computed per run, then aggregated per (workload, profile, policy) cell.

| Metric | Definition | Missing-value rule |
|---|---|---|
| `correct_completion` | tasks that are `succeeded` AND ground-truth correct, over task count | never null |
| `false_success_rate` | tasks `succeeded` but incorrect, over tasks `succeeded` | null when nothing succeeded (not 0) |
| `unsafe_final_status` | incorrect-outcome tasks whose final status is `succeeded`, over incorrect-outcome tasks | null when there are no incorrect outcomes |
| `duplicate_effect_rate` | non-repeatable tasks whose effect executed more than once, over non-repeatable tasks | null when the workload has no non-repeatable task |
| `dependency_order_violations` | count of tasks dispatched before every dependency succeeded | never null |
| `effects_after_cancel` | count of effects begun after the cancel request | null outside the `cancel` profile |
| `makespan_ms` | simulated time until the policy ends the run (flagged `incomplete` when capped) | |
| `recovery_rate` | among tasks that suffered at least one worker crash, the fraction that still ended correct | null when no task crashed |
| `tokens_per_correct` | total tokens over correct completions | null when zero correct |
| `attempts` | total attempts dispatched | |

Self-checks recorded per run and reported (not compared between policies): `peak_inflight` and `cap_exceeded` (whether a
policy ever exceeded its concurrency cap), `audit_violations` (invariants I1-I8 re-checked from the run log of every gated
run, independently of the engine), and `incomplete` (run ended by the run-level cap).

Aggregation: mean over runs with a 95% percentile-bootstrap CI (2,000 resamples, seeded).
Latency: P50, P95 and max across runs. Paired comparison: per-seed difference (`gated` minus baseline) with a
bootstrap CI on the mean difference; a result is called better/worse only when the CI excludes 0.

## Amendments made before the final run

1. **Added `naive-parallel-timeout`** (and the gated-vs-it comparison). Development-seed runs (seeds 0..99) showed that
   under `delay` and `mixed` more than half of `naive-parallel`/`sequential` runs were ended by the run-level cap because
   those baselines have no timeouts at all, so most of the measured gap would reflect "has a deadline", which any
   orchestrator can add cheaply. This was a validity decision informed by development seeds only; no held-out seed had
   been run. No fault rate or other parameter was changed.
2. Realized non-repeatable-task proportions are per-workload outcomes of a fixed hash, not exactly 20% (see Workloads).

## Threats to validity

1. The workers are simulated. Fault rates are assumptions, not measurements of any real model.
2. Baselines are simple by design. Stronger baselines would narrow the gap.
3. Ground truth is a deterministic function. Real correctness is harder to specify, and the gate is only as good as the requirements its author writes.
4. Simulated time ignores real scheduling overhead; the engine's CPU overhead is measured separately (`npm run bench:overhead`, see `docs/PERFORMANCE.md`).
5. A requirement set that is incomplete lets false successes through the gate. The benchmark's requirements are complete by construction (digest equality); the report includes a `partial-requirements` experiment that relaxes this.
